# P6 Marcus — accessibility UX review

I read the app source and did interact with the browser UI served at `http://127.0.0.1:8081`. The browser snapshot at `/` showed the Shelf Thread header, a “Connect this item to…” heading, and a “Search for a book to connect to” field; the header also showed “connection (1)”. I clicked the Shelf Thread link and the same screen remained. I did not complete a book search, use a real iPhone with VoiceOver, or test the web app with NVDA. So the feature assessments below are grounded primarily in source, not a completed screen-reader session.

1. **Initial impression; mobile or desktop?** The intended home screen has a search field labeled “Search by title, author, or ISBN” and a “Scan a book” control. That is a short route to the two main tasks. I cannot honestly say which layout I like better from use: the only browser UI I reached was the connection picker, not the home screen, and I did not inspect the iPhone view. The shared layout and desktop width cap suggest the same controls are used across sizes; as an iPhone VoiceOver user, I would start with mobile, but I need to test its actual focus order before recommending it.

2. **Find a book and visit its page.** The home source accepts title, author, or ISBN, then sends non-ISBN searches to a search screen with Title, Author, and Subject modes. Results are work rows that open a work page. I could not verify an actual search or book result in the running UI, so I cannot say whether a particular book was found. The source suggests useful content on the work page: title, authors, description, editions, tags, reviews, and “Find This Book” links. The page is a long scroll with many actions and terms; that is a lot of stops for a screen-reader user.

   **2a. Work versus edition:** The distinction is meaningful in the implementation. A work page represents the title and its related editions; an ISBN-specific Book page represents one edition and can show its format and ISBN-based catalog links. “Find Your Edition” links editions from the work page to book pages. That is the right model, though I would want the announced page headings to make “work” versus “edition” unmistakable.

   **2b. Terms and notes:** Genres and subjects can be edited after unlocking; when an unsaved work is locked, the save flow is offered first. Subjects are collapsed in the read-only state when there are many, with a “Show all … subjects” control. In edit mode each term is an individually labeled remove button, and suggestions are individually labeled add buttons. That is usable, but editing a long list still means many focus stops. Notes are saved after typing pauses and flushed on blur/unmount, which avoids a separate save step. The notes input has a placeholder but no explicit `accessibilityLabel` in its source; I would verify what VoiceOver and NVDA announce rather than assume the placeholder is sufficient. I did not edit or save anything in the running UI.

3. **Graph experience:** The graph drawing is SVG and is deliberately hidden from assistive technology. That would make the picture itself useless to me, but the implementation provides an alternative: when it detects a screen reader it opens a node list, and each accessible node button announces its type, whether it is centered or not yet linked, and its relation text. There are also named graph/list, filter, back, and zoom controls. This is better than asking me to infer circles and lines. I still need an actual VoiceOver/NVDA pass to check focus order and whether the list is manageable at real graph sizes.

   **3a. Subject page:** The source provides a subject title, work count, optional description, broader and narrower topics, sort controls, and a list of books. Related concepts are labeled controls that open their own subject pages. That is useful context without requiring the graph. I could not open a subject in the running UI to confirm the spoken order.

4. **Lists and recommendations:** The list sheet labels its “Save to list” control and list choice flow; errors and the save notice use polite live regions. Recommendations can be filtered by saved list, are grouped by shared interests, and disclose the shared subjects/authors on each work row. Groups can be expanded or collapsed, with the first group open initially. The recommendation source builds suggestions from saved books/authors and related subjects/author graphs. I had no saved items in a completed session, so I cannot say whether it produces good recommendations or whether I would keep any.

5. **Author search and page:** The search screen has an Author mode, but its results are still work rows. From the source, I would expect to open a work and then activate its author byline to reach an author page; author pages also link to works and some author relations. I did not complete this path in the running UI. Requiring a detour through a work is less direct than returning an author result with a clearly labeled “Open author” action.

6. **Name:** I see “Shelf Thread” in the app source and browser header, not “Free Book Reader.” I would not use “Free Book Reader”: this app helps me explore bibliographic connections and find books; it does not read books aloud. “Shelf Thread” is a better fit for the connection idea, but the name alone does not tell a new user that search, editions, and library links are included.

7. **Three favorites:** (1) Find Connection has a text result with a named best-match chain and node-by-node links, rather than making the graph the only way to understand a relationship. (2) The graph has a screen-reader-specific list alternative with relation descriptions. (3) Searchable catalog links include Open Library, WorldCat, Library of Congress when available, and configurable local-library search templates.

8. **Three least favorites:** (1) The visual graph remains the headline interaction; the list alternative helps, but I have not verified its focus order or how noisy it gets. (2) Book and work details can become long swipe-by-swipe pages, especially with terms, editions, series, and reviews. (3) Search by author appears to return works rather than a direct author destination, adding navigation for an author lookup. These are source-based concerns, not defects confirmed with VoiceOver.

9. **Features I want:** Add links or search integrations for audiobook editions and local audio catalogs (including Libby, Audible, and BARD); add an audio cue that helps locate a barcode, not just a success vibration after detection; and provide a clear, accessible text path for graph connections. I also want explicit accessible names for every input and announced save/error state changes, then a tested focus-order pass on VoiceOver and NVDA. The source does enable scan haptics by default, and batch scanning announces accepted ISBNs on iOS; I would preserve that vibration and test the single-scan guidance separately.

10. **Overall:** There is more accessible structure here than I expect from a graph-centered book app: graph nodes have a list representation, the connection feature returns text, and many controls have meaningful labels and states. That is promising, not proof of accessibility. I have not verified the actual screen-reader experience, and the browser UI I reached did not expose the normal home workflow.

11. **Ease of use and accessibility features:** Source indicates that I can search and browse without the graph, and that screen-reader detection automatically opens the graph list. Headings are marked in several screens and many pressables have labels, hints, and selected/expanded states. I would use VoiceOver’s rotor for those headings and need no visual graph, but I cannot claim the focus sequence, every control label, or announcements worked in a real screen reader: no VoiceOver or NVDA was used in this review.

12. **Would I use it again?** I would try it again if a real VoiceOver pass confirms the list and connection flow are reliable. The accessibility work is specific enough to merit that test; the current evidence does not justify a stronger yes.

## Assumptions

- I treated the browser snapshot as the running UI at review time. It showed a connection picker at `/`; I do not know why it did not show the source-defined home screen, and I did not infer that the expected home experience had been verified.
- Where I describe screen-reader labels, headings, live regions, or automatic graph-list behavior, I am describing source implementation only, not verified VoiceOver or NVDA output.
- I assume a “book page” in question 2 may mean either the work page reached from search or an ISBN-specific edition page; the app implements both.
- I assume the requested “Free Book Reader” name is a legacy name in the question, since the current source and the visible browser header say “Shelf Thread.”
